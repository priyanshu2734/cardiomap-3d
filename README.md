# CardioMap 3D

Track A prototype (Multimodal AI Hackathon 2026): predicts overall CAD and LAD / LCX / RCA stenosis from clinical features and maps the estimates onto an interactive 3D heart, with SHAP explanations. Research and education only; not a diagnostic device and not a substitute for formal diagnostic imaging.

## Quick start
Needs Python 3.11+ (tested on 3.12). From this folder:

    python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
    pip install -r requirements.txt
    python run_demo.py                                   # checks dependencies and model files, then starts the app

Open http://localhost:8000/app. `run_demo.py` retrains automatically if `model.joblib` was made with a different scikit-learn version. Manual route: `python train.py data.xlsx --rebuild-extras` (about 5 min; `--quick` skips nested validation), then `uvicorn app:app --port 8000`.

## What it does
- **Models:** logistic regression, random forest and gradient boosting per target; the best by ROC-AUC is kept. Imputation and scaling are fitted inside each CV fold. Cath, LAD, LCX and RCA are never inputs (asserted in `core.py` and `train.py`).
- **3D viewer (`/app`):** rotate, zoom and select LAD / LCX / RCA; vessel colour follows the predicted probability; optional halo shows the bootstrap range. Vessel paths are schematic, not patient anatomy. Bundled heart meshes: HuBMAP HRA, CC BY 4.0 (`static/models/ATTRIBUTION.txt`). Loading BodyParts3D meshes is optional.
- **Explanations:** per-patient SHAP (LinearExplainer / TreeExplainer), a global importance card ("What drives the model overall", `GET /shap/global`), and the Cardiac Signal Trace with typical myocardial territory.
- **History (`/history`):** every prediction from every section (Dashboard, What-If, Digital Twin, AI Detective, Stress Test, Case Replay, What Next) is logged with its inputs. It is stored only in the browser (`localStorage` key `cm-history-v1`, newest 500), never on the server. Filter by section, expand inputs, reload a case into the dashboard, export CSV/JSON. The recorder is `static/history.js`; tests: `python tests/test_history.py`.
- **Other pages:** `/whatif`, `/trust-center`, `/app/digital_twin`, `/validation` (Validation Report), `/assistant` (optional AI chat), `/architecture`. Extras beyond Track A; see `docs/dev-notes/`.

Model choice is made inside each training fold, so these are not inflated by model selection. Threshold 0.5.

| Overall CAD | gb | 216/303 | 0.87 | 0.90 | 0.92 | 0.91 | 0.92 (0.88-0.95) |
| LAD | rf | 177/303 | 0.79 | 0.79 | 0.86 | 0.82 | 0.85 (0.80-0.90) |

## Data
Z-Alizadeh Sani coronary artery disease dataset, extended version (UCI Machine Learning Repository; also on Kaggle), 303 patients: `data.xlsx`. Original work: Alizadehsani R. et al., "A data mining approach for diagnosis of coronary artery disease", Computer Methods and Programs in Biomedicine 111(1), 2013. Labels: CAD = Cath is "CAD"; vessel = "Stenotic" (at least 50% narrowing). Dropped: Weight and Length (BMI covers them) and Exertional CP (constant). Check the exact citation and DOI on the UCI page before publishing.

## API
`GET /health /schema /metrics /audit /shap/global /docs`; `POST /predict` (probabilities, 80% bootstrap range, SHAP), `POST /explain` (SHAP only). Set `CARDIOMAP_ORIGINS` to restrict CORS.

## Extending
- **New input feature:** add a row to `UI` in `core.py` (id, column, label, group, kind, min, max, step, unit); the form, API schema and model use it. Re-run `train.py`.
- **New model:** add a factory to `MODELS` in `train.py`; it joins the CV, nested CV and selection.
- **New anatomy or vessel:** add a .glb under `static/models/` and extend the vessel table in `index.html`; colours read the same `res[target].p`.
- **Rebuild derived files** after retraining: `python train.py data.xlsx --rebuild-extras`.

## Tests
`python tests/smoke_test.py` checks data, leakage exclusion, prediction, SHAP additivity and the API (steps are skipped, not failed, when `shap` or `fastapi` is missing). Further tests: `tests/`.

## Cardiac Research Lab (`/research-lab`)
**Use case, "pre-angiography triage":** a chest-pain patient arrives; using only non-invasive data (demographics, history, vitals, labs, ECG, echo), how well can we rank who likely has significant CAD (at least 50% stenosis) and in which vessel (LAD, LCX, RCA) before an invasive angiogram? Every result is framed as "what this means for triage", never as a diagnosis. Educational decision support, not a substitute for formal diagnostic imaging.

**Where things are:** page `research_lab.html` (Research menu, light and dark, 1360 / 768 / 390 px); backend `research_lab.py`, endpoints `GET /api/research-lab/meta`, `POST /api/research-lab/run`, `GET /api/research-lab/status/{job_id}`, `GET /api/research-lab/result`. Additive: no change to `core.py`, `model.joblib` or existing API shapes, no new dependencies. Write-up and demo material: `docs/RESEARCH_LAB_METHODS_AND_FINDINGS.md`, `docs/RESEARCH_LAB_DEMO_SCRIPT.md`.

**Run it:** start the app as usual, open `/research-lab`, press *Run experiment* on a card. Runs happen in a background thread (one at a time) with a progress bar and are cached on disk in `.research_lab_cache/`, keyed by experiment, parameters, seed, `data.xlsx` hash and code hash, so an identical request returns instantly. This zip ships the cache for the default settings (seed 0, 2 repeats, 1000 bootstraps), so all five cards load immediately; any change to `research_lab.py`, `core.py`, `train.py` or `data.xlsx` makes it recompute. On one CPU a cold run takes about 4-5 min (ablation), 1.5-2 min (models), 1.5 min (weak vessel), under 20 s (subgroups); calibration is near-instant after the others because experiments 3-5 share one set of out-of-fold predictions per target.

| # | Experiment | Question | Main outputs |
|---|---|---|---|
| 1 | `ablation` | Which kinds of data add ranking power? | AUC per cumulative tier (demographics & history, + labs, + ECG, + echo) for CAD/LAD/LCX/RCA, paired delta with 95% CI |
| 2 | `models` | Does algorithm choice matter? | Logistic regression vs random forest vs gradient boosting, paired delta vs best |
| 3 | `weakvessel` | Why are LCX and RCA harder than LAD, and would more data help? | Class balance, vessel overlap, per-fold variance, learning curve, labelled reasons |
| 4 | `subgroups` | Do results look similar by sex and age band? | Descriptive only: n, prevalence, AUC, sensitivity, specificity, small-group warnings |
| 5 | `calibration` | Can the scores be read as probabilities? | Reliability curve, Brier score and skill, calibration slope, patients per probability band who truly had the condition |

**Protocol (all experiments):** Cath, LAD, LCX and RCA are never inputs (asserted in `core.py`, again on every run, and the feature groups must partition the input columns exactly). Stratified nested CV: outer repeated 5-fold with fixed seeds and the same splits for every comparison; inner stratified 3-fold ROC-AUC selection on the training part only; imputation and scaling fitted inside folds. Out-of-fold probabilities are averaged over repeats; threshold 0.5. 95% CIs are percentile bootstraps over patients with shared resamples, so differences are paired. "Within noise" means the paired CI for the AUC difference includes 0; that is not proof of equivalence. Every result carries a manifest: experiment id, parameters, seed, UTC time, SHA-256 of `data.xlsx` and of the code (`research_lab.py`, `core.py`, `train.py`), library versions. JSON and CSV export on every card; finished runs are kept in this browser (`cm-research-lab-v1`, newest 12) and logged in History.

**Key results (seed 0, ROC-AUC with 95% CI; details in the methods note):** overall CAD ranks well (0.91, 0.87-0.94 with all non-invasive data); LAD is moderate (0.85, 0.80-0.89); LCX (0.75, 0.69-0.80) and RCA (0.71, 0.65-0.77) are weak and clearly below LAD (differences -0.10 and -0.13, both beyond noise). Raw scores are not literal probabilities (CAD calibration slope 1.71, 1.36-2.24).

**Known limitations**
- One public cohort of 303 patients already referred for angiography (71% have CAD). No external validation; absolute performance will not transfer to an undifferentiated chest-pain clinic.
- LCX/RCA estimates, and every subgroup estimate, are imprecise (CIs about +/-0.06 for the vessels, wider in subgroups). Groups with fewer than 20 patients in the rarer class are flagged; below 10 the AUC is withheld. Subgroup results are descriptive: no tests, no fairness claim.
- CIs come from resampling patients' out-of-fold predictions. They do not capture retraining variability and are not corrected for multiple comparisons.
- The lab uses all 53 non-invasive columns, not the 25 dashboard inputs, so its numbers differ from the deployed model and the table above. Whether any non-target column is only known after angiography rests on the dataset documentation; only Cath/LAD/LCX/RCA are excluded by rule.
- Calibration: logistic regression and random forest use balanced class weights, which shifts raw probabilities. No recalibration is applied. Each probability is an average over CV repeats.
- Learning curve: the largest size is about 80% of the cohort, and the model family is the one chosen most often in the nested run (a small selection effect). It cannot show what happens with more patients than that.
- The "why LCX/RCA are harder" reasons are partly measured (class balance, vessel overlap) and partly general clinical reasoning that this data cannot test; the page labels each.
- Jobs run in-process, one at a time, and are lost on server restart (the disk cache survives). The code hash covers three Python files, not the HTML.
- Tested here without FastAPI installed: the HTTP route test is skipped, and the page was checked in Chromium against a stdlib mock server that calls the same `research_lab` functions. Visual checks covered 390 px light and 1360 px dark only; 768 px, Firefox/Safari and screen readers were not tested.

**Tests:** `python tests/test_research_lab.py` (numeric checks against scikit-learn, leakage rejection, fixed-seed reproducibility, cache and manifest, small-n warnings, an end-to-end run of experiments 3-5), `python tests/test_research_lab_ui.py` (static page checks), `python tests/test_architecture.py`.

## Heart Function Lab (`/heart-function`, Research menu)
A teaching page: a real-anatomy reference heart (HuBMAP Human Reference Atlas male heart, CC BY 4.0) beats at about 72 bpm (systole, then diastole, with a phase label, speed control and pause) and three coronary tubes (LAD, LCX, RCA) can be selected by click, label or button to read what each feeds and what a narrowing can cause. Captions on the canvas: "Reference anatomy, not your heart" and "Simplified physics model, not patient-specific or clinical". The dataset has no imaging, so the page never detects or locates a lesion and has no scan upload.

**Where things are:** page `heart_function.html`; module `heart_function.py` (manifest checks, mesh route; `GET /api/heart-function/manifest`, `GET /heart-function/mesh/{name}`); manifest `static/models/heart_function_mesh.json` (title, author, source URL, licence, SHA-256, triangle counts, vessel control points, animation landmarks). The mesh route serves only the file named in the manifest, only `.glb`/`.gltf`, refuses path parts and symlink escapes, and refuses to serve unless the licence is CC0, CC-BY, CC-BY-SA or public domain. Additive: no change to `core.py`, `model.joblib` or existing API shapes; Three.js r128 and the GLTFLoader pattern are reused from the dashboard.

**Performance:** 127,178 of the mesh's 164,119 triangles are drawn (internal valves and papillary muscles are skipped; budget 150k), pixel ratio capped at 1.5, rendering stops when the tab is hidden or the canvas is off screen, and the heart starts paused under `prefers-reduced-motion`. If WebGL or the 3D library is unavailable the vessel guide still works.

**Blood flow:** `static/coronary-flow.js` is a pure, DOM-free module (works in the browser and in node) holding the lumped teaching model: each artery has a radius r0, length L and resting flow; a narrowing of d% diameter at a fixed position gives rs = r0(1 - d/100); the pressure drop across it is dP = Rv Q + Rt Q^2 (Rv proportional to 1/rs^4, Rt proportional to (1/As - 1/A0)^2); the small vessels downstream widen to hold flow until their reserve is used up. A Rest / Exercise toggle sets demand to 1x or 3.5x resting flow. Outputs per artery: flow as a share of demand, a reserve gauge, peak capacity vs resting flow, and a plain state (Flow maintained / Reserve reduced / Flow limiting). Inflow pulses with the beat and is highest in diastole. Blood particles follow continuity (speed = Q / lumen area: faster in the narrowing, slower and thinner beyond it when flow falls short). The tube is green below 50%, amber 50 to 69%, red from 70%; below 50% is not counted as a stenosis in this dataset. Equations, constants and assumptions are in the page's "How this works" panel (constants are printed from the module, so they cannot drift). Teaching values only: not patient-specific or clinical. Tests: `node tests/test_coronary_flow.js` (monotonic flow and reserve, rest tolerates more narrowing than exercise, 50/70% bands, equations, pulse mean and diastolic peak, continuity, particle coordinate, and that the module's beat curve equals the page's).

**Known limits (phase 2 / later extensions):** the mesh has no labelled coronaries, so the tubes are schematic paths snapped to the outer surface along the anterior interventricular and the two atrioventricular grooves. Chambers move as rigid parts (exaggerated). The current lab can show one or two example narrowings in series; the two-lesion extension assumes the lesions are far enough apart not to interact. Branch paths, dominance and collateral flow are teaching controls, not patient anatomy or measurements. Particle counts are illustrative.

**Wall effect, ECG, your estimate, History (phase 3 of 4):** `static/heart-effects.js` is a second pure module (browser and node). *Severity* per artery is 0 below 50% narrowing, else 0.35 (reserve lost) + 0.65 (flow shortfall) from the flow model at the chosen activity, so Exercise shows an effect at a smaller narrowing than Rest. Each ventricle vertex carries typical-territory weights (LAD, LCX, RCA; angle around the left-ventricle long axis, turned so the drawn LAD groove is the anterior/anteroseptal boundary; LAD takes over towards the apex; right ventricle is RCA). A shader darkens the wall by up to 55% and weakens its local squeeze by up to 30% (slightly) in proportion to weight x severity. An illustrative one-lead ECG (3 beats, scrolls with the heartbeat, dashed = normal) lowers its ST segment by up to 0.30 mV as 1 - prod(1 - severity). Both are captioned illustrative; equations and constants (printed from the module) are in "How this works".
**Your estimate:** the page reads the dashboard's shared snapshot (`localStorage` `cm-case-v1`, read only; the same one Signal Trace and the Trust Center read through `case-handoff.js`) and shows LAD/LCX/RCA probabilities, the 80% range when present, and the top 3 SHAP drivers for the selected artery as "your estimate". It only preselects the artery with the highest probability and offers a suggested start (p >= 0.65: 70%, 0.40 to 0.65: 50%, below: none) that is applied only when you press "Use as starting point", with the note "A starting point from the model, not a measured blockage". No snapshot: "Run a prediction on the dashboard".
**History:** a settled configuration with a narrowing (1.5 s after the last change, identical repeats dropped) is logged as "Heart function run" through `window.cmHistory` (`kind: heartfn`): the three narrowings, Rest/Exercise, the primary artery's flow state in the label, and the estimates that were on screen (none if no snapshot). `history.js` now accepts that kind without a probability; the History page labels it and links back to the lab.
**Fix found while testing:** `/static/coronary-flow.js` was missing from the static allow-list in `app.py`, so the phase-2 flow card would have been hidden in the real app (the stdlib mock server did not use that list). Both new scripts are now listed and `tests/test_heart_function.py` checks every `/static/` file the page loads against the real allow-list.
**Tests:** `python tests/test_heart_function.py` (runs everything below), `node tests/test_heart_effects.js` (gate at 50%, exercise-first, monotonic severity, territories on the real mesh incl. each drawn vessel path sitting on its own territory, ECG ST maths, estimate parsing, preselection and suggestion), `node tests/test_history_recorder.js` (heartfn kind), `python tests/visual_qa/heart_fx.py` (Chromium, light and dark at 1360/768/390: overflow, button contrast, estimate present/absent, click-only application, ECG, History row).
**Known limits (wall/ECG phase):** territories, named branches, dominance and collateral flow are teaching patterns and amounts; none is read from the dashboard snapshot. The ECG is one invented lead; the 3D wall shader needs Three.js r128 from the CDN and was not rendered in the build sandbox (no network), so check it once in a real browser; a run is logged per settled configuration, not per slider tick.

**Physics-vs-data cohort check:** inside `#pvd`, the page pairs the live flow curve with a separate descriptive cohort panel. The curve asks what this simplified physics model does as narrowing increases; the cohort panel asks what was recorded among the same 303 referred patients. The cohort API (`heart_cohort.py`, `GET /api/heart-function/cohort?vessel=LAD|LCX|RCA`) returns aggregates only: group sizes, counts, rates and Wilson 95% intervals for the fixed finding whitelist that is actually present in `data.xlsx`. It excludes angiography/leakage columns using the same `core.LEAK` rule, flags small groups and sparse findings, and keeps LCX/RCA estimates explicitly weak. The cohort check never changes the simulation, feeds no model input, and is not a validation of the physics. The page uses the API's constants/findings in its "How this works" panel so the explanation cannot drift from the implementation.

**Documents and final verification:** `docs/HEART_FUNCTION_LAB_METHODS_AND_LIMITS.md` records what is real, what is teaching-only, what is descriptive-only, and what the data cannot show. `docs/HEART_FUNCTION_DEMO_SCRIPT.md` includes the original Heart Function Lab segment plus a 30-second Physics-vs-data beat. Run the Heart Function, cohort, architecture, curve, wall-effect, History, and visual-QA checks listed below; run the full `tests/` directory as well before release. Browser-only checks require a working Chromium/Playwright environment.

**Known limitations (whole lab):** the physics model is a teaching model, not patient-specific or clinical; its narrowing thresholds are model outputs, not clinical cut-offs. Coronaries are schematic tubes because the reference mesh has no labelled coronaries; sequential lesions use a simplified series-resistance model, branches are schematic side-branch controls, and collateral flow is a capped teaching parameter. Dominance, branches and collateral flow are chosen in the lab and are not patient-specific. The wall/ECG effects are illustrative. The cohort rates are descriptive only: one referred cohort, no external validation, no causal inference, and no p-values as proof of anything. LCX and RCA groups are smaller than LAD and the estimates are weak. The EF-TTE below-50% rule is a fixed descriptive choice, not a diagnostic threshold. The data are tabular only, contain no imaging and cannot show lesion location/shape on a user's heart, cannot validate the physics model, and cannot establish that an observed finding was caused by a recorded narrowing. Patient-level rows are never returned by the cohort endpoint. In this sandbox, Chromium visual QA may remain unavailable; when that happens it is reported as NOT RUN rather than silently treated as passed.

**Heart Function Lab — phase 5 additions:** `static/heart-physio.js` reads the dashboard snapshot (`cm-case-v1`) read-only. PR is used only when it is finite, 40–130 bpm and measured; EF-TTE is used only when it is present and 15–65%. Otherwise the lab uses reference values of 72 bpm and 60% EF. A fixed 120 mL end-diastolic volume is an illustrative teaching constant, not a patient measurement. Heart rate changes beat timing and the normalized diastolic pulse shape but not the coronary model's mean flow; EF changes rigid-part motion amplitude relative to EF 60%.

**Removed from the Heart Function lab:** the "Typical myocardial territory" panel (17-segment bullseye, segment details, Clear marks and RWMA cross-check) is no longer on `heart_function.html`. `static/heart-segments.js` stays in the repo but the page no longer loads it. The paragraphs below describe the earlier Phase 5 build.

**17-segment companion and RWMA teaching overlay:** `static/heart-segments.js` reuses `CM_SEGMENTS` from `static/case-handoff.js` rather than maintaining a second territory table. The inline SVG bullseye uses the dashboard's Low/Moderate/High probability bands and symbols, with visible `V` markers where supply varies. Segment paths are keyboard-operable and focusable. `static/heart-effects.js` assigns LV/septum vertices to one of the 17 segments once at mesh setup. **RWMA cross-check:** the dataset supplies only the `Region RWMA` count, not segment identities. The lab therefore compares the user's marked segments with the model's highest-ranked LAD/LCX/RCA vessel as a teaching exercise. **Known limits (phase 5):** the heart-rate/EF response is a teaching animation, not a physiological simulator; the EDV is fixed and not measured; HR does not alter the flow equations or mean flow. The 17-segment assignment is a typical AHA-style territory map, not patient-specific anatomy; dominance and anatomical variants remain. **Phase 5 audit fixes (found by testing against a dashboard-shaped snapshot):**
- The dashboard stores `vals` and `nm` by field **id** (`pr`, `ef`, `rwma`); the lab looked them up by dataset **column** (`PR`, `EF-TTE`, `Region RWMA`), so with a real snapshot the heart rate, EF and RWMA count silently fell back to reference values. `HeartPhysio.normaliseCase()` now maps ids to columns through the snapshot's own `ui` table (column keys still pass through).
- The RWMA cross-check was passed the whole estimate object instead of the probabilities, so it always compared against LAD. `HeartSegments.concordance()` now accepts the `parseCase()` shape or a flat map, and refuses to guess from non-numeric values.
- The ECG now scrolls with the active beat length (it was fixed at 72 bpm), and the beat phase is kept when the rate changes.
- Marked segments keep their risk-band colour under a hatch overlay (before, the hatch replaced the fill); the bullseye `<svg>` is `role="group"` (an `img` role hides its focusable segments from assistive technology); one low-contrast label was darkened.
- History no longer drops a second Heart Function run whose marked segments differ but whose counts and estimate match.
- Tests now use a realistic snapshot (ids, `ui` table) so these cannot regress; the browser QA measures every text node instead of the container colour. Not run here: the 3D wall shader (Three.js r128 is loaded from a CDN, unreachable offline), and the FastAPI HTTP routes.

**Heart Function Lab — phase 6 additions:** The uncertainty card applies the existing `HE.suggest()` three-level teaching rule (0/50/70%) to the model 80% range and then runs the unchanged `CoronaryFlow` solver. It is read-only and does not alter the narrowing controls. `static/heart-wiggers.js` draws cached illustrative aortic/LV pressure, LV volume, ECG and selected-artery coronary inflow traces from the active beat; rate comes from the id-keyed dashboard snapshot and systolic BP is used only when it is finite, 80–200 mmHg and measured, otherwise 120 mmHg is used as a teaching reference. `static/heart-compare.js` keeps a page-memory A configuration and compares it with the live B configuration or the two built-in presets; compare actions are not written to History. **Known limits (phase 6):** the uncertainty sweep is model-range exploration, not an anatomical range; the example 0/50/70% narrowing is a coarse teaching translation. The pressure/volume traces are analytic teaching curves, with fixed teaching assumptions for EDV (120 mL) and diastolic pressure (80 mmHg, capped at systolic minus 25 mmHg); they are not patient measurements. Stenosis is shown in the trace card only through the existing ECG ST effect and selected-artery coronary inflow; it does not alter the pressure/volume equations. Compare Mode shows differences between two settings of the same teaching model, not a clinical comparison.

## Optional AI assistant
Copy `.env.example` to `.env` and add a GROQ or NVIDIA key. Never commit `.env`. Not needed for anything above.


**Heart Function Lab — sequential narrowing and anatomy teaching controls:** `static/coronary-flow2.js` adds an optional second lesion in series with the first. With the second narrowing at 0%, it delegates to the existing `CoronaryFlow.solve()` path so the default single-lesion numbers remain unchanged. The two example lesion centres are fixed at the vessel's existing `at` position and `at + 0.30` (clamped to 0.86), with the documented assumption that they are far enough apart not to interact. The combined drop is `(Rv1+Rv2)Q + (Rt1+Rt2)Q²` plus the healthy remaining-length term and the same healthy-artery `rmin` used by the original model.

`static/heart-anatomy.js` adds three page-memory teaching controls: a right/left dominance toggle, named diagonal/obtuse-marginal/PDA side branches, and a collateral-flow slider capped at **35% of territory demand**. The right-dominant teaching row is exactly today's **LAD 0.45 / LCX 0.29 / RCA 0.26** share. The left-dominant teaching row is **LAD 0.45 / LCX 0.35 / RCA 0.20**; its LCX/RCA resting-demand split is **82.73 / 47.27 mL/min** while preserving their combined baseline demand. The PDA parent switches from RCA to LCX. Branch origins and shares are schematic constants: diagonal at 0.48 with 0.20 of parent-territory demand, obtuse marginal at 0.55 with 0.25, and PDA at 0.78 with 0.35. No branch is inferred from the dashboard and no branch-specific narrowing slider is presented. Collateral effective flow is `antegrade + min(c × demand, shortfall)` and never exceeds demand; steal is not modeled.

**Decision gates:** Gate **S = PRIMARY** because the default uncertainty sweep remains unchanged, `HE.suggest()` is called with its existing parsed-probability shape, and the sweep's middle point matches the same effective-flow function across arteries, modes and non-default anatomy contexts. Gate **H = ELSE** because the browser rendering check for old History entries without the optional fields was not runnable in this sandbox; therefore the new anatomy/second-lesion/collateral settings are not written to History, while the existing `heartfn` settled-run shape stays unchanged. Compare actions remain unlogged.
